# Why embed an EVM in your process?

> You know what would make solving all these problems trivially easy? If we just were able to use Foundry in JavaScript.

That thought is how [Fucory](https://x.com/fucory) started Tevm. Most Ethereum tools treat the TypeScript application and the Ethereum node as two separate worlds connected by a brittle local port. You run one tool to compile Solidity, a second tool to generate types, a third process to run a fork on `localhost:8545`, and then hope parallel tests do not stomp on each other's nonces.

Tevm's premise is simple: **TypeScript + EVM in one toolkit.**

> We believe every TypeScript user of the EVM who installs Viem will also install Tevm alongside it.

## 1. Zero daemon friction, real native speed

An external dev node (`anvil`, `hardhat node`) owns one shared process and one shared port. Every test file fights over the same chain state unless you orchestrate port pools and cleanup scripts.

With Tevm, `createMemoryClient()` instantiates a fresh native ZEVM engine inside your Node.js process:

- **Parallel tests never collide.** Each test creates its own isolated chain state and releases it with `await client.tevmClose()`.
- **Native execution speed.** Bytecode runs in Zig (Guillotine Mini + Voltaire) over a C ABI — not a pure-JavaScript interpreter.
- **Deterministic genesis.** Local chains start at block `0`, timestamp `0`, chain ID `31337`, with 10 prefunded dev accounts.

## 2. One engine for tests, backends, and browser dev servers

Early Tevm releases ran an EthereumJS engine in the browser. Shipping a full EVM in JavaScript meant maintaining two divergent execution implementations and paying JS interpreter overhead.

Tevm now runs a single native engine (ZEVM) in Node.js (`>=24`):

- **Tests and Node.js services** talk directly to the native addon in memory with zero network serialization overhead.
- **Browser frontends and wallets** connect to the exact same engine over HTTP or WebSocket using `tevm/server` (`pnpm native:server` or `createServer(client)`).
- **AI coding agents** drive isolated EVM sessions over stdio using `@tevm/mcp`.

<UnderTheHood title="Why native Node-API instead of a browser JS EVM?">
One execution engine means one source of truth for hardfork semantics, gas accounting, tracing, and fork behavior. Node-API lets Node.js call ZEVM directly in-process, while `tevm/server` serves HTTP batches, WebSocket `eth_subscribe` streams, and Unix IPC to any browser or external process.
</UnderTheHood>

## 3. Import Solidity like TypeScript

Running contracts from TypeScript shouldn't require a separate codegen step every time you edit a function signature.

The optional **Tevm Bundler** (`tevm/bundler/*`) and `@tevm/ts-plugin` teach your bundler and editor how to compile `.sol` files directly:

- NatSpec comments on hover in your editor
- Red underlines before you save the Solidity file
- Full `abitype` inference for `read`, `write`, `events`, and `deploy`
- Resolves both `node_modules` and Foundry `remappings.txt` / `foundry.toml`

```ts
import { Counter } from './Counter.sol'

console.log(Counter.abi)
```

## 4. Built for debugging, not guesswork

When a transaction reverts on a forked contract, a generic `"execution reverted"` string wastes an hour. Tevm returns structured native revert data (`{ code: 3, data: '0x...' }`) and exposes native opcode tracing via `debug_traceCall` — complete with pre-op stack, memory, gas cost per step, and revert bytes.

```ts
import { createMemoryClient } from 'tevm'

const client = createMemoryClient()
try {
  const target = '0x0000000000000000000000000000000000000123'
  await client.tevmSetAccount({
    address: target,
    deployedBytecode: '0x602a60005260206000f3',
  })

  const trace = await client.transport.tevm.request({
    method: 'debug_traceCall',
    params: [{ to: target }, 'latest', { enableMemory: true }],
  })

  console.log(trace)
} finally {
  await client.tevmClose()
}
```
