# Forking upstream chains

A Tevm fork reads accounts, contract bytecode, and storage slots lazily from an upstream JSON-RPC endpoint and stores every local write in an in-memory overlay. It never copies the entire chain and never writes upstream.

## Create a reproducible fork

Pass `fork: { url, blockNumber }` alongside the matching `chainId` and `common`:

```ts
import { createMemoryClient } from 'tevm'
import { mainnet } from 'tevm/common'

const client = createMemoryClient({
  chainId: mainnet.id,
  common: mainnet,
  fork: {
    url: 'https://ethereum-rpc.publicnode.com',
    blockNumber: 20_000_000,
  },
})

try {
  await client.tevmReady()

  const vitalik = '0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045'
  const balance = await client.getBalance({ address: vitalik })
  console.log('Forked balance:', balance)
} finally {
  await client.tevmClose()
}
```

- **`url`** — any HTTP(S) Ethereum JSON-RPC endpoint.
- **`blockNumber`** — optional unsigned safe integer (`number`). Pin it in tests so every run sees identical state. Omit it to fork from the upstream head at startup.
- **`chainId` / `common`** — configure the chain ID (for example `mainnet.id` = `1`) so signed transactions and EIP-712 domain separators match the forked network.

## Read upstream, mutate locally

The first uncached read fetches the account, code, or storage slot from the upstream endpoint and caches it locally. Any write (`tevmSetAccount`, `tevmDeal`, `setBalance`, `setCode`, or a mined transaction) updates only the local overlay.

```ts
import { createMemoryClient, parseEther } from 'tevm'
import { mainnet } from 'tevm/common'

const client = createMemoryClient({
  chainId: mainnet.id,
  common: mainnet,
  fork: {
    url: 'https://ethereum-rpc.publicnode.com',
    blockNumber: 20_000_000,
  },
})

try {
  await client.tevmReady()

  const target = '0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045'
  const before = await client.getBalance({ address: target })

  await client.tevmDeal({ address: target, amount: before + parseEther('100') })
  const after = await client.getBalance({ address: target })

  console.log({ before, after, delta: after - before })
} finally {
  await client.tevmClose()
}
```

## Isolate fork tests with snapshots

Fetching state from a remote RPC takes a network round trip on the first cache miss. Combine a shared fork setup with `snapshot()` and `revert()` so each test rewinds local writes without reforking:

```ts
const snapshotId = await client.snapshot()

await client.setCode({
  address: '0x1111111111111111111111111111111111111111',
  bytecode: '0x602a60005260206000f3',
})

await client.revert({ id: snapshotId })
```

## Two critical fork semantics

<QaBox question="Why does getBlockNumber() return 0n right after forking block 20,000,000?">
ZEVM forks upstream **state** at your pinned `blockNumber` into a fresh local chain starting at block height `0`. It does not import historical upstream block headers. Accounts, code, and storage slots read lazily from the pinned upstream block, while blocks mined locally increment from `0` → `1` → `2`.
</QaBox>

<WatchOut title="Never fork a server running on the same Node.js event loop">
ZEVM performs fork HTTP requests **synchronously inside native Zig code**. If a test spawns an HTTP mock server on the same Node.js event loop and tries to fork it from the same process, the native HTTP call blocks the JS thread that would have answered the request — causing a deadlock.

In tests that fork a local upstream server, run the upstream server in a **child process** (`node:child_process` `fork()` or `spawn()`).
</WatchOut>

## Operational summary

| Behavior | Detail |
| --- | --- |
| Startup | `createZevmEngine` runs `anvil_reset` with `{ forking: { jsonRpcUrl, blockNumber } }`. |
| Invalid URL / unreachable RPC | `tevmReady()` rejects with a `NativeRpcError` and releases the native handle automatically. |
| Repeated reads | Served from the local cache without another network round trip. |
| Switching fork blocks | Call `anvil_reset` with new `forking` params, or create a new client. |
