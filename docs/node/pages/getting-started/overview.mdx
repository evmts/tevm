# Quickstart

You want to deploy a contract, inspect its state, or test a transaction against live mainnet contracts — without booting Docker, managing a background Anvil port, or burning RPC rate limits.

With Tevm, the Ethereum node lives inside your Node.js process.

## 1. Install Tevm and viem

Requires **Node.js 24 or later**.

:::code-group

```bash [pnpm]
pnpm add tevm viem
```

```bash [npm]
npm install tevm viem
```

```bash [yarn]
yarn add tevm viem
```

```bash [bun]
bun add tevm viem
```

:::

## 2. Boot an in-process chain and send ETH

Save this as `quickstart.mjs` and run `node quickstart.mjs`:

```ts
import { createMemoryClient, parseEther, PREFUNDED_ACCOUNTS } from 'tevm'

const client = createMemoryClient({
  mining: { auto: false },
})

try {
  const sender = PREFUNDED_ACCOUNTS[0].address
  const recipient = '0x1111111111111111111111111111111111111111'

  // 1. Submit a transaction to the mempool (not mined yet)
  const { txHash } = await client.tevmCall({
    from: sender,
    to: recipient,
    value: parseEther('1'),
    addToMempool: true,
  })

  // 2. Mine a single block so the transaction becomes canonical
  await client.tevmMine({ blocks: 1 })

  // 3. Query the mined receipt and new balance with standard viem actions
  const receipt = await client.getTransactionReceipt({ hash: txHash! })
  const balance = await client.getBalance({ address: recipient })

  console.log({ status: receipt.status, balance })
  // { status: 'success', balance: 1000000000000000000n }
} finally {
  // Always release the native engine handle when done
  await client.tevmClose()
}
```

### What just happened?

1. `createMemoryClient({ mining: { auto: false } })` allocated an isolated native ZEVM chain (chain ID `31337`, block `0`, 10 prefunded accounts with 10,000 ETH each) and attached viem public, wallet, test, and TEVM actions.
2. `client.tevmCall({ ..., addToMempool: true })` dispatched `eth_sendTransaction` and placed the transfer in the pending pool.
3. `client.tevmMine({ blocks: 1 })` ran `anvil_mine`, committed the state transition, and indexed the receipt.
4. `getTransactionReceipt` and `getBalance` read the canonical state back through viem.
5. `client.tevmClose()` freed the native Zig runtime.

<ExecutionFlowDiagram />

<QaBox question="Why did I pass mining: { auto: false }? What happens if I omit it?">
Automining is **enabled by default** (`mining: { auto: true }`). If you omit `mining`, every transaction you submit mines its own block immediately and you do not need to call `tevmMine()`.

Turn automining off when you want to inspect the mempool, batch multiple transactions into the same block, or control block boundaries explicitly in a test.
</QaBox>

<WatchOut title="Always close the client">
Each `createMemoryClient()` owns an isolated native ZEVM handle. Call `await client.tevmClose()` in a `finally` block (or `afterEach` in tests) to release native memory and stop any background interval-mining timer.
</WatchOut>

## 3. Deploy and call a contract

You can either deploy real creation bytecode with `tevmDeploy`, or inject runtime bytecode at any address with `tevmSetAccount` for instant unit tests.

```ts
import { createMemoryClient, parseAbi } from 'tevm'

const client = createMemoryClient()

try {
  // Creation bytecode that deploys a contract returning uint256(42)
  const deployed = await client.tevmDeploy({
    bytecode: '0x600a600c600039600a6000f3602a60005260206000f3',
  })

  const result = await client.tevmContract({
    address: deployed.createdAddress!,
    abi: parseAbi(['function answer() view returns (uint256)']),
    functionName: 'answer',
  })

  console.log('Deployed at:', deployed.createdAddress)
  console.log('answer() =>', result.data) // 42n
} finally {
  await client.tevmClose()
}
```

<UnderTheHood>
`tevmDeploy` encodes constructor arguments if you pass `abi` and `args`, submits the creation transaction, and mines it automatically unless you pass `addToMempool: true`. Once mined, `deployed.createdAddress` holds the new contract address from the native receipt.
</UnderTheHood>

## 4. Fork an upstream chain

Point `fork.url` at any JSON-RPC endpoint and pin `blockNumber` for reproducible tests. Missing accounts, code, and storage load lazily on first access; local writes stay inside your process.

```ts
import { createMemoryClient } from 'tevm'
import { mainnet } from 'tevm/common'

const client = createMemoryClient({
  chainId: mainnet.id,
  common: mainnet,
  fork: {
    url: 'https://ethereum-rpc.publicnode.com',
    blockNumber: 20_000_000,
  },
})

try {
  await client.tevmReady()

  const vitalik = '0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045'
  const balance = await client.getBalance({ address: vitalik })
  console.log('Forked balance:', balance)

  // Mutate locally — never touches mainnet
  await client.tevmDeal({ address: vitalik, amount: balance + 1n })
  console.log('Local balance:', await client.getBalance({ address: vitalik }))
} finally {
  await client.tevmClose()
}
```

<QaBox question="Wait — why is await client.getBlockNumber() equal to 0n on a fork?">
ZEVM forks upstream **state** at your pinned `blockNumber` into a fresh local chain starting at height `0`. It does not import historical upstream block headers. Reading accounts, contract code, and storage slots falls through to the upstream RPC at the fork block, while every new block you mine starts at `1`, `2`, `3`, and so on.
</QaBox>
