# Migrating from tevm 1.0.0-next.x to 1.0.0

This guide covers the public changes that matter to applications moving from
the prerelease line to 1.0.0. The examples were executed against the published
`tevm@1.0.0-next.149` and `tevm@1.0.0-rc.151` packages with their declared viem
peer ranges.

## Install the stable packages together

Keep all directly installed `tevm` and `@tevm/*` packages on the same version.
They are a linked Changesets release group. The stable aggregate package expects
viem `^2.49.3` at the release-candidate baseline.

```sh
pnpm add tevm@1.0.0 viem@^2.49.3
```

If the application directly installs low-level packages, update those to
`1.0.0` in the same change.

## Create the client synchronously

`createMemoryClient()` returns the client, not a promise. Some older examples
used `await` during construction. Awaiting a non-promise happened to work, and
the published `next.149` was already synchronous, but the stable form makes the
lifecycle clear.

Before:

```ts
import { createMemoryClient } from "tevm"

const client = await createMemoryClient({
  miningConfig: { type: "manual" },
})
await client.tevmReady()
```

After:

```ts
import { createMemoryClient } from "tevm"

const client = createMemoryClient({
  miningConfig: { type: "manual" },
})
await client.tevmReady()
```

Both snippets were run. In both published packages,
`typeof client.tevmReady === "function"` was true and the returned value had no
`then` property.

Calling `tevmReady()` is optional for normal use because actions wait for the
node internally. Keep it when startup must complete before timing or exposing
the client to another process.

## Use the EIP-1193 request shape

The stable high-level provider method takes only `method` and optional `params`.
It returns the RPC result directly and throws a `ProviderRpcError` for an RPC
error. Do not pass `jsonrpc` or `id`, and do not pass the old second
retry-options argument.

Before, for the low-level JSON-RPC envelope:

```ts
import { createMemoryClient } from "tevm"

const client = createMemoryClient()
const blockNumber = await client.transport.tevm.request({
  jsonrpc: "2.0",
  id: 7,
  method: "eth_blockNumber",
  params: [],
})
console.log(blockNumber)
```

After, for an EIP-1193 consumer:

```ts
import { createMemoryClient } from "tevm"

const client = createMemoryClient()
const blockNumber = await client.request({
  method: "eth_blockNumber",
  params: [],
})
console.log(blockNumber)
```

The before snippet returned `0x0` on `next.149`. The after snippet returned
`0x0` on `rc.151`. Keep the low-level form only when code must construct or
serve complete JSON-RPC envelopes.

## Update interval mining units and keys

Manual and automatic modes keep the stable forms
`{ type: "manual" }` and `{ type: "auto" }`. Interval mining is now implemented
by the node, and its duration is expressed in seconds.

Before:

```ts
import { createMemoryClient } from "tevm"

const client = createMemoryClient({
  miningConfig: {
    type: "interval",
    interval: 1000,
  },
})
console.log(client.transport.tevm.miningConfig)
```

After:

```ts
import { createMemoryClient } from "tevm"

const client = createMemoryClient({
  miningConfig: {
    type: "interval",
    blockTime: 1,
  },
})
console.log(client.transport.tevm.miningConfig)
```

The snippets were run with an explicit process exit so the timer could not keep
the verification process alive. They printed
`{"type":"interval","interval":1000}` on `next.149` and
`{"type":"interval","blockTime":1}` on `rc.151`.

The `GasMining` type and the `{ type: "gas", limit }` strategy are gone. Use
manual mining and call `tevmMine` when the application decides a block is full.

## Account for canonical blocks, txpool, and receipts

Use `miningConfig: { type: "manual" }` when a test needs to inspect pending
transactions. A transaction-producing Tevm call stays pending until mined.
Cheat actions such as `tevmSetAccount` still mutate the active state directly.

The following stable flow was run against both `next.149` and `rc.151`:

```ts
import { createMemoryClient } from "tevm"

const client = createMemoryClient({
  miningConfig: { type: "manual" },
})

const before = await client.request({ method: "eth_blockNumber" })
await client.tevmMine({ blockCount: 2 })
const after = await client.request({ method: "eth_blockNumber" })

console.log({ before, after })
```

It printed `{ before: "0x0", after: "0x2" }` on both versions.

For raw pool inspection, 1.0.0 implements `txpool_content`,
`txpool_contentFrom`, `txpool_inspect`, and `txpool_status`. Prefer viem public
actions for blocks, transactions, and receipts where an equivalent action
exists. The stable handlers resolve canonical blocks and support fork fallback,
legacy receipts, and block receipt queries.

## Update package entry points

The low-level packages used by existing adopters remain public in 1.0.0.
`@tevm/memory-client`, `@tevm/evm`, `@tevm/actions`, `@tevm/node`, and
`@tevm/common` were all published at `1.0.0-rc.151` and are part of the linked
stable release group. Existing direct imports can stay if the application
intentionally owns those low-level dependencies.

The aggregate package also exposes equivalent subpaths. The following direct
and aggregate imports were both executed successfully against `rc.151`:

Before, with separate package dependencies:

```ts
import { createMemoryClient } from "@tevm/memory-client"
import { createTevmNode } from "@tevm/node"
import { mainnet } from "@tevm/common"
import * as evm from "@tevm/evm"
import * as actions from "@tevm/actions"

console.log(
  typeof createMemoryClient,
  typeof createTevmNode,
  mainnet.id,
  typeof evm.createEvm,
  typeof actions.callHandler,
)
```

After, when consolidating on `tevm`:

```ts
import { createMemoryClient } from "tevm/memory-client"
import { createTevmNode } from "tevm/node"
import { mainnet } from "tevm/common"
import * as evm from "tevm/evm"
import * as actions from "tevm/actions"

console.log(
  typeof createMemoryClient,
  typeof createTevmNode,
  mainnet.id,
  typeof evm.createEvm,
  typeof actions.callHandler,
)
```

Both printed `function function 1 function function`. Do not mix prerelease and
stable versions across the aggregate and direct packages.

## Replace removed historical surfaces

`@tevm/core` stopped at `1.0.0-next.12`. Its contract factory moved to the
contract package and was renamed.

Before:

```ts
import { createTevmContract } from "@tevm/core"

console.log(typeof createTevmContract)
```

After:

```ts
import { createContract } from "tevm/contract"

console.log(typeof createContract)
```

The before import was run against `@tevm/core@1.0.0-next.12`, and the after
import was run against `tevm@1.0.0-rc.151`. Both printed `function`.

The historical generic `@tevm/bundler` and Optimism-specific
`@tevm/opstack` packages are not part of 1.0.0. Replace `@tevm/bundler` with the
specific compiler or plugin surface the application uses, usually
`tevm/bundler`, `tevm/bundler/compiler`, or a
`tevm/bundler/*-plugin` subpath. Replace `@tevm/opstack` chain configuration
with the appropriate preset from `tevm/common`; normal fork behavior belongs
on `createMemoryClient({ fork, common })`.

The named bundler plugin packages still exist. In particular,
`@tevm/esbuild-plugin` is not removed in rc.151. The preferred consolidated
entry point is `tevm/bundler/esbuild-plugin`.

Before:

```ts
import { esbuildPluginTevm } from "@tevm/esbuild-plugin"

console.log(typeof esbuildPluginTevm)
```

After:

```ts
import { esbuildPluginTevm } from "tevm/bundler/esbuild-plugin"

console.log(typeof esbuildPluginTevm)
```

Both imports were run against `rc.151` and printed `function`. Equivalent
aggregate subpaths exist for the other named plugins:

- `@tevm/vite-plugin` remains supported; consolidation target:
  `tevm/bundler/vite-plugin`
- `@tevm/webpack-plugin` remains supported; consolidation target:
  `tevm/bundler/webpack-plugin`
- `@tevm/rollup-plugin` remains supported; consolidation target:
  `tevm/bundler/rollup-plugin`
- `@tevm/rspack-plugin` remains supported; consolidation target:
  `tevm/bundler/rspack-plugin`
- `@tevm/bun-plugin` remains supported; consolidation target:
  `tevm/bundler/bun-plugin`

`@tevm/ts-plugin`, `@tevm/unplugin`, and `@tevm/requirejs-plugin` also remain
separate packages. They do not have matching aggregate subpaths in 1.0.0.

## Other breaking details

- Use chain presets from `tevm/common`. The transient `tevm/chains` entry point
  was added and removed between prereleases.
- `client.request(args, retryOptions)` is now `client.request(args)`.
- viem must satisfy `^2.49.3` at the rc.151 baseline.
- Low-level Ethereum execution classes are backed by the Tevm ZEVM facade.
  Code that depends on exact `@ethereumjs/*` class identity should switch to
  the types exported by `tevm/tx`, `tevm/vm`, `tevm/state`, and related
  subpaths.
- EIP-6800 Verkle execution is intentionally unsupported.
  `StateManager.initBinaryTreeExecutionWitness` no longer exists, and a block
  that activates this execution path is rejected with a typed error.
- The top-level `IntervalMining` type is no longer exported from `tevm`. Import
  mining types from `tevm/node`.

## Trace and simulation changes

The stable RPC surface includes `debug_traceCall`, block and transaction trace
methods, `flatCallTracer`, `muxTracer`, `eth_simulateV1`, `eth_simulateV2`, and
Anvil-compatible trace controls. Check tracer output rather than relying on
prerelease snapshots: stable structured-log depth is 1-based, gas cost avoids
double-counting, and failed calls derive failure from the execution result.
